# 真实业务验收操作约定

本目录与 `tests/fixtures/business/` 交付 AWR-QA-002 的场景准备。8 套材料通过接入检查，不等于 8 个业务场景通过。真实业务执行属于 AWR-QA-003；状态只由 `ledger/work-ledger.yaml` 和其证据决定。

当前版本范围见 [V1 合同](../../contracts/awr-v1.json)、[Fixture 合同](../../tests/fixtures/business/contract.json)、[覆盖矩阵](coverage.md)与[证据硬门槛](../../tests/fixtures/business/gate-contract.json)。各目录的 `scenario.json` 保存操作方使用的完整定义，`project/` 保存实际客户端初始可见的业务来源，`prompts/` 只保存自然输入，`updates/` 保存尚未发布的后续材料。

## 执行前

1. 完成主台账为真实验收规定的前置工作，确认当前源码、构建、客户端接入和各方权限。准备工具不会替这些门槛提供通过结果。
2. 为本次执行创建新的 run ID 和目录，核实场景 namespace、工作图、运行根目录与来源哈希。不得沿用接入验证目录、先前产物、回复或运行态。
3. 将参与者槽位绑定到实际身份与客户端记录。执行者、并行执行者和独立复核者必须可区分。跨客户端场景需要实际不同客户端以及原生 MCP 工具轮次；修改 provider/model 标签不算。
4. 当前主项目限制自动分派子代理。Fixture 里的角色定义不授予分派或启动模型客户端的权限；实际执行方式应在具备授权和客户端条件后落实。身份或权限尚未落实时，真实验收保持未执行，并继续可独立推进的工作。
5. 有 prelude 的场景先在实际客户端产生前序工作、产物和运行回执，再进入规范的自然发起。会话变化、中断、并行所有权及前序分支必须真实发生，不能靠准备程序预写数据库。

## 完整业务过程

只将自然业务输入提交给真实用户使用的客户端。不要把测试编号、内部对象 ID、预期答案、状态机步骤或评审要点混入输入。业务来源中的正常任务标识与材料事实仍由 AWR 按需提供；操作方的评判材料和尚未到达的追问不能提前发给执行者。

保留首轮用户输入、实际工具或角色执行、产物与来源引用。第一轮产物真实存在后，暂停对相关来源的编辑，由资料作者发布第一轮补充材料，再提交第一轮自然追问。保留有业务意义的修订和解释。随后以同样方式执行第二轮追问，不用一次改写同时抵充两轮。

`prepare.py publish-round` 只发布新的业务输入，不会发送用户消息、调用模型、推进 AWR 工作状态或通过任何业务门槛。若来源已被其他参与者修改，它应拒绝覆盖。若发布中断，保留现场，按 pending 标记和前后摘要核对每个文件后再决定恢复方式，不重复盲跑。

执行者处理完两轮变化后，将实际产物、引用与过程交给独立复核者。复核者使用每个场景的 rubric 逐条核对结论，记录缺陷；返工和复核后的结论都须保留。由执行者给自己生成一段“独立复核通过”文字不构成复核。

最终交付包含业务产物、两轮修订、复核结果和未决事项处置。每个场景单独提交交付材料并核实远端 SHA，绑定实际客户端记录、源码及产物哈希。先前用于初始化合成来源的 seed commit 不属于独立业务交付提交。

## 证据与边界

使用 [运行记录模板](run-record.template.json)整理原始证据位置；空字段和空证据列表保持未完成，不能填造身份、时间、工具结果或复核结论。模板仅供记录，不是自动通过器。每个 required gate 都需有可读取、范围匹配的记录，不能用布尔值、平均分、接口探针或同质简单样本补足。

实际 E4 操作来自真实客户端。后端、接口和数据库仅用于只读取证；不要直接改它们来制造会话、认领、恢复、证据或已完成状态。对未授权资料的限制同样适用于执行者使用的其他工具。

受限材料场景的长日志为公开合成记录，日志行与批次不是同一计数单位；受限原件存放在客户端项目外，未授权时只列资料缺口。公开交付须核对引用范围，不把受限材料或未知原因补成确定结论。

遇到未获授权、客户端不可用、无法重现真实中断、缺少独立复核或待复测时，保留原因、现场与恢复条件，按主台账记为未完成。可继续其他独立工作，但不能计入 8 个完成场景。大型真实项目与 10 个性能/恢复指标仍按各自工作项验证。
